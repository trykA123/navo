# P42 · Compare and merge

Status: after the alpha. It does not start until the alpha is done, unless the owner says otherwise. Decided (D70); Q2 answered 2026-10-20; Q1 open, architect defaults apply until answered · Repo: `navo` · Branch: `p42-<atom>` per atom · Started: 2026-10-20

## Goal

The user can compare two folders, two Git refs of one repository (branch, tag, commit, HEAD, index, working tree) or two repositories in Navo's two panes, without checking anything out. The user can open any changed pair as a full-window file diff, edit a real side, and copy a file or a hunk to the other side with the old version kept. Then, before 1.0, three-way merge: a branch pair or a conflicted file opens with its merge-base, and the user resolves every conflict before saving. Navo replaces Beyond Compare for this work and adds what it lacks: Git refs as folders, an included three-way merge with automatic base, and every write through a plan, a journal and undo. Files of any practical size compare in full in the first version: large text gets a line diff that opens at once and fills in, binary files get a hex diff, and huge files in a folder compare are checked in the background.

## Spec for people

What the user can do, in plain words. The decisions below make it exact.

- **Start a compare.**
  - Right-click → "Compare with other pane" (D46), or Ctrl+K → "Compare with other pane".
  - Ctrl+K → "Compare branches…" picks two refs of the repository the active pane is in.
  - Typing `C:\src\navo@main` in the path bar opens that branch read-only in the pane, like an archive. Two panes on two refs, then "Compare with other pane".
- **Folder compare lives in the two panes.** Rows line up. A file that exists on one side only leaves a blank gap on the other. Each row has a status colour: same, different, only left, only right, type conflict (file against folder), case conflict (Windows), unavailable (with the reason), and "same after rules" (for example only line endings differ). Rows still being checked say "checking", and the totals say so too.
- **Moving.** Enter on a folder enters it on both sides. Backspace goes up on both. Enter on a file pair opens the file diff. Alt+↓ / Alt+↑ jump to the next or previous difference. Esc clears the filter first, then leaves compare mode.
- **Filters.** All, Differences, Orphans, Same. The usual type-to-filter works on names. `.gitignore` rules apply by default; "Show ignored" brings ignored files back. A user ignore list lives in settings.
- **Walk every changed file, like Beyond Compare (owner, 2026-10-30). Superseded by D113 (2026-11-09): the Stream (Alt+F) shows every changed file in one scroll; Ctrl+Alt+↓ / Ctrl+Alt+↑ in the file diff still step through the same list. See Part V.** From a folder compare, "Open all differences" (Ctrl+K, and Enter on a folder row with Shift) opens the file diff for the first changed pair in that folder tree, recursively. Ctrl+Alt+↓ / Ctrl+Alt+↑ go to the next or previous changed file without leaving the diff; Ctrl+B lists every changed pair (path, status, a count of changed lines) and jumps on Enter. The list follows the active filter and ignore rules. Orphans open as one-sided views, binary pairs in the hex diff. Esc returns to the folder compare on the row of the last file seen.
- **File diff opens full-window, like F3.** It opens calm (D58): two sides, changed lines tinted. Changed words are marked inside lines that pair up with a similar line on the other side. Ctrl+B opens the list of differences, Ctrl+I the details (encoding, line endings, hashes, active rules), Alt+V the View menu: Simple (line diff), Rich (changes inside a line, syntax colours, the overview strip), Custom. Options: ignore whitespace, line endings, case, BOM. A raw difference that the options hide is still named in the details.
- **Big text files.** Any text file opens in the diff at once, whatever its size. The top lines up within a second; the rest fills in with a progress line, and scrolling never waits. A memory limit in Settings → Compare (default 1 GiB) decides how much detail very large changes get. A part too big for it shows as one changed block, and the status line says so and links to the setting. Navo never falls back to "same or different" only.
- **Binary files.** Binary files open in a hex diff: two hex columns, changed bytes tinted, Alt+↓ / Alt+↑ between differences. Files of equal size line up by offset. Files of different sizes line up by content, so an inserted block shows as a gap and the rest stays aligned. Alt+V switches any pair between Text and Bytes.
- **Big files in a folder compare.** Rows show size and time at once. The content check runs in the background, visible rows first, with progress on large rows, and stops at the first difference. "Stop checking" ends it for one row or all rows. Hashes are remembered, so comparing the same files again is instant.
- **Never stuck.** No file can make a compare hang. Each step has a limit; past it, Navo shows a simpler result for that part and says so in the details.
- **Editing.** A side that is a real file can be edited. Typing never waits for the diff; the marks update a moment after you stop. Its encoding, BOM and the ending of every line are kept. Save refuses when the file changed on disk since it was read. A Git ref side is read-only. A side over 64 MiB is read-only in the first version; copying hunks and files still works.
- **Copying.** Ctrl+Alt+→ / Ctrl+Alt+← copy the current hunk (in the diff) or the current file row (in the panes) to the right or left. Each copy is one job with a journal. The old version is kept until Navo closes; "Restore previous version" brings it back. Folder sync (many rows, both directions, deletes) waits for the delete safety net (D65) and job undo.
- **Copy only the lines you pick (owner, 2026-10-30).** In the file diff, Shift+↑/↓ or a drag over the line numbers selects lines on one side, also across hunks; Space ticks or unticks single lines inside a hunk. Ctrl+Alt+→ / Ctrl+Alt+← then copies only the selected lines: a selected changed line replaces its paired line on the other side, a selected line that exists only on this side is inserted at its aligned place, and the rest of the hunk stays as it was. Ctrl+Shift+Del removes the selected lines that exist only on this side. With nothing selected the keys copy the whole current hunk, as before. One copy is one undo step, and the hunk splits so the lines left out stay marked as different.
- **Mouse users (owner, 2026-10-30).** Hovering a change shows a small labelled bar over it: "← Copy to left · Copy to right →" (no bare arrows). Changed lines get a tick box in the gutter, shown on hover and while any line is picked; Shift+click picks a range. Right-click on any line opens a context menu with everything the keys do: copy picked lines, copy this line, copy this change left/right, remove picked lines, pick this line or the whole change, next/previous difference, copy text, ignore whitespace; Shift+F10 or the Menu key opens it at the cursor line. Prototype: compare-p42.html direction 4, File diff.
- **Git engine.** Settings → Compare → Git engine: "Installed Git" (default), "Built-in (gitoxide)" or "Automatic". Without an installed Git, Navo uses the built-in engine and says so once.
- **Merge (before 1.0).** "Merge branches…" or opening a file Git left in conflict shows base, ours and theirs with a result. One-sided changes are taken automatically. A counter shows the unsolved conflicts; Save stays off until it reaches zero. Whitespace-only conflicts resolve in bulk. `navo compare` and `navo merge` serve `git difftool` and `git mergetool`.

## Decisions

Final. Workers never reopen them; a worker that finds one wrong stops and reports.

- **D1 — Parts and order.** Each part ends in a review, `cargo xtask gate`, Windows CI and a merge.
  1. Part S: facts and spikes.
  2. Part E (engine), Part G (Git) and Part L (large and binary files) in parallel. Each Part L atom waits for the Part E atoms it names.
  3. Part J: copy and save.
  4. Part U: screens. The designer round U0 can run once S3 is done.
  5. Part Y: folder sync. Blocked until D65 and job undo ship.
  6. Part M: three-way merge, before 1.0.
  - Under the about-15-atoms rule the orchestrator may save the parts as `p42a`…`p42h` plans, with these decisions shared.
- **D2 — Components (D13, D62).** Compare is a first-party module with internal Rust interfaces. Dependencies point down.
  - `navo-compare`: new, GUI-free, no Navo UI or store dependency (Skein can adopt it, D40). It depends on `navo-core` only, plus `imara-diff`, `similar` 3.x, `blake3`, `ignore`, `xxhash-rust` (line keys), `fastcdc` (byte diff) and `ropey` 1.6 (edited sides, D21). `memmap2`, if S4 earns it, lives in `navo-app` only (D19).
  - `navo-git`: new, read-only. The `GitSource` trait, both engines, the engine registry.
  - `navo-fs::git`: the `repo@rev` read-only provider (ProviderId `git`).
  - `navo-app::compare`: adapters (side sources, hash cache, engine choice) and the background session.
  - `navo-ui::compare`: pane mode, file diff, later the merge view.
- **D3 — Git engines (D70 item 2).**
  - One trait, `GitSource`, two engines. `CliGit` drives the installed `git`: one long-lived `git cat-file --batch-command --buffer` per comparison session, `ls-tree -r -z -l`, `merge-base`, `diff-tree`/`diff --raw`, `for-each-ref`, `cat-file --filters`. `GixGit` runs `gix` in-process.
  - Setting `[compare] git-engine = "git" | "gix" | "auto"`, default `"git"`.
    - `"git"`: the CLI. Any repository format the user's Git can create reads correctly (Git 3.0 defaults: SHA-256 objects, reftable refs).
    - `"auto"`: gix for SHA-1 repositories with the files ref backend, the CLI otherwise.
    - `"gix"`: gix, with a per-repository fallback to the CLI and a visible note when the format is unsupported.
    - No installed `git`: the default falls back to gix with a notice. A repository gix cannot read then shows "Install Git to compare this repository".
  - The format check reads `extensions.objectFormat` and `extensions.refStorage` from the repository config before choosing (`RepoFormat`).
  - Work gix does not do (filters with drivers such as LFS, worktree status with the stat cache) always goes to the CLI when Git is installed, under every setting.
  - Merge-base also always goes to the CLI when Git is installed (amended 2026-10-30): on criss-cross merges gix and Git can pick different bases from `merge-base --all`. Without Git, gix answers, any member of that set is accepted, and the note is logged.
  - Engines register through an internal engine registry (the module system, D13/D62). A module could add another engine later. The settings page lists the registered engines.
  - Every CLI call: `--end-of-options` before user refs, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `LC_ALL=C`, no console window on Windows. Navo never writes into `.git`.
  - The CLI needs Git 2.36 or newer (`--batch-command`). Older Git counts as "not installed" for this choice.
- **D4 — Git is the oracle.** Status between Git sides comes from Git's own change lists (`diff-tree -r -z --raw --no-renames A B`; `diff --raw -z --no-renames <rev>` against the working tree, which uses Git's stat cache and filters). Equal object ids skip content reads. CI checks gix against the CLI on the navo repository; the paperwing repository runs locally through `NAVO_ORACLE_REPOS`.
- **D5 — Status model (from Skein).** Every row has a raw status (bytes) and a display status (after rules). "Same after rules" is never hidden as "same". A refresh bumps a generation; a write planned on an older generation, on a "checking" row, on a link, a submodule or an unavailable row is refused. No cap fails a whole comparison; limits are per row and name their reason.
- **D6 — Content check.** Order: kinds, object ids, sizes, cached BLAKE3, then the lockstep read with BLAKE3 alongside (D19), with cancel. Never a whole file in memory for the check. The hash cache is a `content-hash` table in `CacheDb`, keyed by provider, path, size, modification time and file id.
- **D7 — Diff (D70 item 5).** `imara-diff` Histogram for lines, over the whole file in the Whole tier and inside each section in the Sections tier (D8, D16), `similar` 3.x for changes inside a line, only on visible rows, lines over 4,096 characters count as whole-line changes. `navo-core` stays on `similar` 2.7 for now; two versions are acceptable (D44). S2 confirms the choice first.
  - Pairing (from delta): inside a hunk, consecutive removed and added lines form a subhunk. Lines pair by the smallest edit distance with a greedy pass; a pair whose distance passes 60 % of the longer line stays unpaired (S2 tunes it). Word marks go only inside paired lines; unpaired lines stay whole deletes or inserts and face a filler row. Subhunks over 200 lines per side pair in order (D20).
- **D8 — Text sides and size tiers (Q2: no size wall).**
  - Each side decodes on its own (encoding, BOM, per-line endings); the encoding comes from the first 64 KiB. Binary means a NUL in the first 8,000 bytes, as Git does. Binary pairs open in the byte diff (D18).
  - No size limit. Two tiers, chosen per pair:
    - **Whole:** both sides at most 64 MiB. Sides load into memory; whole-file Histogram (D7). Editing works here.
    - **Sections:** either side over 64 MiB. Sides stay on disk as `ByteSource`s and are read in 1 MiB blocks; the diff runs per section (D16). Hunk copy streams (J6). Free editing waits; the side says "Read-only above 64 MiB; copy hunks or the file".
  - Local files are read with positional reads (`ByteSource::read_at`), not memory maps. Reason: a mapped file that another program truncates crashes Navo on Linux (SIGBUS) and on Windows makes that program's truncation fail (log rotation breaks). An open diff view never maps a file. The short folder content check may, under D19's ripgrep rule.
  - A Git blob over 64 MiB streams once into a spool file under Navo's cache folder. Spool files are deleted when the view closes and at start-up.
  - A side that changes on disk during a diff restarts it with "Changed on disk, comparing again" (`take_changed`).
- **D9 — Writes (D70 item 4).**
  - A new `Step::WriteFile { target, staged, expect }` writes edited text or an applied hunk. `staged` is a temp file on the target's volume; `expect` is the stamp (size, modification time, BLAKE3) of the version the user saw. A changed stamp refuses the step.
  - Copying from a Git ref uses a source reader for another provider (shared with archive extraction).
  - Before D65 and job undo: copies are one file row or one hunk at a time. Compare jobs keep their held old files until Navo closes, and "Restore previous version" brings the last one back. Copies never delete destination-only files.
  - Folder sync (many rows, both directions, recycle) is Part Y and waits for D65 and a job undo command.
- **D10 — Where it lives (D70 item 3).** Folder compare is a mode of the two panes. File diff and merge open full-window on the F3 viewer host. D58 applies: calm open, Ctrl+B, Ctrl+I, Alt+V with Simple, Rich and Custom.
- **D11 — Keys.** Context `Compare` (pane mode) and `CompareView` (file diff, merge). All rebindable (D49), with labels in `compare.ftl`. See the key table.
- **D12 — Editable aligned sides.** S3 decides between A (two editable gpui-kit editors with filler rows, scroll-locked) and B (a read-only aligned view; Enter on a hunk edits that hunk in place on one side). U7 builds the S3 verdict. Either way Save goes through `WriteFile`.
- **D13 — Merge (Part M).** Our own diff3 on `imara-diff`. The replay oracle compares with `git merge-file` on every merge commit of navo and paperwing. Conflict markers in merge, diff3 and zdiff3 styles are parsed. Save stays off until the unsolved count is zero. Navo never stages: after saving a file from an unmerged index, it says "Saved. `git add <path>` marks it resolved" with a Copy button.
- **D14 — Tests in proportion.** Many tests for Git reading, filters, merge correctness and copy safety; few for screens.
- **D15 — Who builds what.** Sonnet `api-builder` for decided backend; Sol 6.1 xhigh (Codex) for backend atoms with many edge cases; Opus `senior` for Git processes, filters, Windows, data safety and hard interaction; Sonnet `ui-builder` for decided UI; Opus `designer` once per view family before its UI atoms; `reviewer-senior` per part; `reviewer-cross` (Sol high) on every job, journal and process-spawning diff.
- **D16 — Large text diff.**
  - **Scan.** Each side is read once, both in parallel. The scan builds the sparse `LineIndex` and the xxh3-64 hash of each line's normalised key. A line is an anchor candidate when its hash falls in 1 of K buckets (K = 32 until S4 sets it) and it has at least 8 non-blank bytes. Only candidates are kept, 16 bytes each.
  - **Anchors.** Candidates unique on each side and present on both match. The longest increasing run of matches (patience) splits both files into section pairs. Anchor lines are compared byte for byte when their section is read; a hash collision drops the anchor.
  - **Sections.** Each pair is read back and diffed exactly with D7's Histogram. A pair over the section cap (1M lines or 64 MiB per side until S4 sets it) re-anchors with a denser sample (K/8, down to every unique line). Then D17 applies.
  - **Progressive.** The view opens at once on the first page of both sides. A provisional diff of the first 4 MiB of each side aligns the top. After the scan, sections diff top-down on at most four workers, the section in view first (`focus`). Arriving hunks never move the top visible line.
  - **Moving.** Next difference jumps to known hunks; past them it shows "Looking further… N %" and jumps when one arrives; Esc stops the wait. Rows are built for the viewport only, from the sorted hunk list and the line index.
  - **Targets**, two 1 GB log files (about 10M lines each, at most 1 % of lines changed):
    - first screen aligned under 1 s;
    - full diff under 4 s warm, under 8 s cold;
    - every frame while scrolling under 16 ms; a jump to any line under 50 ms;
    - compare working memory under 256 MiB.
  - **Assumed Windows PC class** until measured: Windows 11, 8 cores with AVX2, 32 GB RAM, NVMe SSD at 2 GB/s or more, files on a local disk. Warm means both files are in the OS cache. windows-latest (4 vCPU) may take twice as long. S4 measures; the owner checks on a Windows PC.
- **D17 — Memory budget, never a wall.** `[compare] memory-budget-mib`, default 1024, range 256–16,384. It caps the compare engine's own memory for one open diff (section working sets, anchors, hunk list, byte regions), not the OS file cache. Above it, detail drops step by step, per section, never for the whole file. The status line names the step and links to the setting.
  1. **Whole** (D8): whole-file Histogram; changes inside lines in Rich.
  2. **Sections:** the same result in nearly every file; Ctrl+I says "Aligned in N sections".
  3. **Coarse block:** a section pair still over the cap after re-anchoring, or over the budget, shows as one changed block. It keeps exact line ranges and counts, pages both sides side by side, and has no changes inside lines.
  4. **Paged hunks:** when the hunk list passes a quarter of the budget, only sections near the view keep line-level hunks. The rest keep counts and are diffed again when scrolled to (under 100 ms per section).
  - Changes inside a line run on visible rows only, so they cost no budget and are not a step of their own. They are off for lines over 4,096 characters (D7) and inside coarse blocks. A line over 1 MiB offers "Show bytes here" (D18).
  - Equal regions are always aligned, and every changed region has exact line ranges. No step shows "same or different" only.
- **D18 — Byte diff, in the first version.**
  - Binary pairs open in it. Alt+V → Bytes switches any pair to it, and Text switches back.
  - Two hex columns (16 bytes per row, offset, ASCII) built from the F3 viewer's hex rows. Changed bytes are tinted; Alt+↓ / Alt+↑ go to the next or previous region.
  - **By offset** (default for equal sizes): both sides are read in lockstep 1 MiB blocks. Differing ranges closer than 16 bytes merge into one region. Regions arrive top-down.
  - **By content** (default for different sizes): FastCDC chunks (min 2 KiB, average 8 KiB, max 64 KiB) with a BLAKE3 hash each, matched with D16's anchor step over chunks unique on both sides. The gaps are changed, inserted or deleted regions. Regions up to 64 KiB per side refine to exact bytes (`similar` over bytes); larger ones stay region-level with the first differing byte. An insertion shows as a gap and the rest stays aligned.
  - Memory: about 40 bytes per chunk, about 5 MB per GB. Over a quarter of the budget, neighbouring regions merge and keep their counts.
  - Read-only in the first version; the file row copy in the panes still works.
  - **Targets**, two 1 GB binaries: hex view open under 200 ms; all regions by offset under 2 s warm, by content under 4 s warm.
- **D19 — Large files in a folder compare (amends D6).**
  - Size and time first. Different sizes are Different at once, nothing read. Equal size and time show "same size and time · checking". Git sides compare object ids first (D4).
  - Guarantee (2026-10-30): Same means the bytes were equal while read, and each side's size and time matched the listing before the read, and its stamp (size, time, file id) did not change during the read. A change between those checks, or an in-place rewrite that restores size and time, is not detected; no file locking. Git and other compare tools give the same guarantee.
  - The content check reads both sides in lockstep 1 MiB blocks with BLAKE3 alongside. The first differing block ends the check: Different, with the first differing offset. Equal to the end gives Same, and both hashes go to the cache. With one side cached, only the other side is hashed.
  - The scheduler (`queue`) checks visible rows first, then smaller files first. Files up to 64 MiB run on as many workers as the machine has cores, at most 12 (ripgrep's cap). Larger files run one at a time per volume, so USB disks, hard disks and network shares do not thrash. Rows over 64 MiB show progress (bytes checked of size), updated at most four times a second.
  - "Stop checking" ends one row's check or all checks within 100 ms. The row then shows "Not checked (stopped)", a final state: a copy may use it, and its plan says the content was not checked.
  - `[compare] content-check = "content" | "size-time"`, default `"content"`. `"size-time"` never reads content; its rows show "same size and time", never "same".
  - The folder view never waits: navigation, filters, Enter and copies work during checks.
  - I/O follows ripgrep: buffered 1 MiB reads by default, which suit many files. Memory maps only when at most 10 pairs are left to check, on local Windows volumes, and only if S4 shows a gain over 30 %. A map lives for that one check, never for an open view (D8). Linux always reads buffered: a truncated mapped file kills the process there.
  - The first NUL in a buffered block marks the row binary (ripgrep's quit mode). Text rules never apply to it; Enter opens the byte diff.
  - Why: the research reports slow Beyond Compare folder compares on USB and network drives, and Beyond Compare offers timestamp+size, CRC and byte-by-byte as separate methods (`research.md`, Beyond Compare section). Navo does one pass that stops at the first difference like byte-by-byte and remembers hashes like CRC, without blocking the view. The research has no evidence about Beyond Compare's large-text or hex compare, so this plan claims no advantage there.
- **D20 — Compare never hangs (from difftastic).** Every diff step has a hard cap and a cheaper fallback, so no input stalls a view or a worker. The caps are named constants in one place, measured by S2 and S4. Ctrl+I names every fallback that ran.
  - Word marks: lines over 4,096 characters (D7), or a pair past `similar`'s 5 ms deadline → whole-line change.
  - Pairing: subhunks over 200 lines per side → in-order pairing.
  - Line diff: `imara-diff` runs in its non-minimal mode, which bounds its cost like Git's. A section or Whole-tier file still running after 2 s on its worker → coarse block (D17 step 3) with the notice. The late result is dropped, and a fresh worker takes the slot (at most two extra per diff).
  - Byte refinement: a region over 64 KiB per side → region level (D18).
  - Syntax-aware diff (D40, after this plan) must use difftastic's caps: sides over 1,000,000 bytes, more than 3,000,000 graph nodes (difftastic's limit, chosen there for about 5 s) or a parse error → this line diff, with a note.
- **D21 — Edited sides diff on snapshots (from helix and ropey).**
  - An editable side's text lives in a `ropey::Rope` (1.6, the stable line; 2.0 is beta). Each edit bumps a version and is kept as an invertible transaction, so undo applies the inverse.
  - The re-diff runs in the background on `rope.clone()`, a cheap immutable snapshot, 150 ms after the last keystroke. A result applies only while its version is current; an older one is dropped. Typing never waits.
  - Whole tier only (D8), under D20's caps. Save writes the bytes of the version on screen (D9).
  - With S3 verdict A, the gpui-kit editor's buffer feeds the rope edit by edit. If S3 finds the editor exposes a cheap snapshot itself, that replaces the rope.

- **D101 — A copy checks the bytes it copies (F1b, from the L8 review and a Sol review).**
  - Metadata alone cannot prove a source is unchanged: a cached page, an edit between stat and read, an empty source range and a same-length same-time edit all pass it.
  - `ByteSource` gains a sticky, non-consuming `revision()` and a fresh `revalidate()` (stat against the open baseline, ignoring the page cache). Both have default bodies, so other implementers compile unchanged. `PagedFile` implements them.
  - The diff hashes the source range of every copyable hunk with BLAKE3 when it produces the hunk. Coarse and paged blocks are not copyable, so they cost nothing.
  - Apply revalidates both sides before and after the copy, re-reads the source range, and refuses with `ApplyError::Changed` on any hash mismatch, empty ranges included. A retry on the same instances stays refused.
  - No save screen ships before F1b lands.

### Spec for people (Part V)

- **Two full-window screens.** The *file diff* shows one pair: the calm Reference look of Direction 4, content at full width, a change map strip on the right edge, one status line. The *Stream* shows every changed file under a folder as cards in one scroll, like a code review.
- **Getting there.** Folder compare in the panes stays as shipped. Enter on a file pair opens the file diff. Alt+F (or Ctrl+K → "Stream all differences") opens the Stream for every difference under the current compare folder.
- **Reading the Stream.** Each card has a header (path, status, `+n −m`, a Viewed tick) and the changes with three lines of context. J / K (or Alt+↓ / Alt+↑) go to the next or previous change in any file. Shift+J / Shift+K (or Ctrl+Alt+↓ / Ctrl+Alt+↑) go to the next or previous file. O folds a card. V marks a file Viewed: the card folds, the header says "Viewed n of N" with a thin bar, and the mark survives a refresh and a restart because it is keyed by the files' content.
- **Into one file and back.** Enter on a card opens that file in the file diff at the current change. Esc returns to the same card. In the file diff, Ctrl+Alt+↓ / Ctrl+Alt+↑ step to the next or previous changed file of the same list. Esc in the Stream closes search, then the outline, then returns to the panes with the cursor on the file of the current card.
- **Calm by default (D58).** Both screens open with drawers closed. Ctrl+B is the outline tree in the Stream and the list of changes in the file diff. Ctrl+I shows details (encoding, line endings, rules, fallbacks). Alt+V opens the View menu: Simple, Rich, Custom; Unified or Side by side.
- **Copying one change (release 2).** Ctrl+Alt+← / Ctrl+Alt+→, or the labelled bar that appears on hover ("← Copy to left · Copy to right →"), copies the current change at once. The change header then says "Copied to the right · Undo". Ctrl+Z undoes it.
- **Searching every difference (release 2).** `/` opens a search field above the Stream. Typing narrows the Stream to the files and changes whose changed lines or path contain the text, and the outline shows hit counts. J / K walk the matches only.
- **Copying all matches (release 2).** With a search active, Ctrl+Shift+← / Ctrl+Shift+→ (or the "Copy all N" button) opens a plan sheet first. It lists each file, its changes and anything refused. Enter runs one job; one Ctrl+Z undoes all of it.
- **Large, binary and image files (release 3).** Until then their cards show sizes and status, with "Open with F3". Release 3 gives them real bodies: a filling line diff for large text, a hex diff, an image diff.
- **Not in Part V.** Editing a side (U9, still after S3), base-aware three-way suggestions (Part M, D113), copying whole files from the Stream, and folder sync (Y2, which reuses the plan sheet).

### Decisions

- **D22 — Look and scope (D113).** The file diff is the P42 Direction 4 Reference. The Stream is explore-2 direction B, with these changes: Alt+V opens the View menu (D58) instead of toggling the layout; files are in path order, not grouped by kind; copying a whole file is out. Free editing stays in the file diff (U9).
- **D23 — Host (amends D10 in letter, not intent).** Both screens are one full-window *compare screen* on `NavoWindow`, drawn where the F3 viewer draws (`window_view/layout.rs:29-32`). They are not a `ViewerBody`: the F3 `Viewer` holds one `Location` and sniffs kinds for it. The compare screen reuses the viewer's header style (`viewer/view.rs`), drawers (`viewer/parts`), View menu builder (`viewer/view_menu.rs`) and status line. The Stream and the file diff stack: the file diff opens on top of the Stream, and Esc pops it.
- **D24 — Boundary.** `navo-ui` stays free of `navo-compare`, as for the pane compare (`browser/compare/hooks.rs`). A new trait `DiffHooks` with plain UI types lives in `navo-ui::compare_diff::hooks`. `navo-app::compare::diff` implements it and is passed in through a new `OpenHooks.diff` field, next to `OpenHooks.compare` (`window_view/hand_off.rs:136-145`, `navo-app/src/gui.rs:317`). All loading, diffing, hashing and searching run on app threads. The UI receives owned `Arc` snapshots tagged with a request id or generation; a stale one is dropped on arrival.
- **D25 — Stream items.** An item is a file row under the compare's current folder, at any depth, whose status is Different, OnlyLeft, OnlyRight, TypeConflict, CaseConflict, Unavailable or Checking. Folders and Same rows are left out. Same-after-rules rows form one folded group at the end. Order: the compare's own path order (folders first, then names, as `navo-compare::pair` sorts), so the outline and the scroll agree. A Checking item shows a "checking" card; it becomes its result, or leaves the Stream when it settles Same. Arriving cards never move the top visible row: the list is a gpui `list` with `ListState`, and arrivals go in with `splice`.
- **D26 — Cards and memory.** A text card shows each hunk with 3 lines of context; an equal run between hunks is one row "N unchanged lines". A card holds at most 2,000 rows; past that, a last row says "N more changes · Enter opens the full diff". Changes inside a line are computed for card rows on the app worker under D20's caps (D7's visible-rows rule protects the UI thread; this keeps that aim). The app keeps card bodies within a quarter of `memory-budget-mib`, at least 64 MiB; the least recently focused body goes first. An evicted card shows a placeholder and is rebuilt when it comes near the view. At most four pairs diff at once, the cards in view first. Release 1 builds bodies for Whole-tier text only (both sides at most 64 MiB, D8). Large-tier text, binary and image pairs get a summary card until release 3.
- **D27 — Keys.** New context `CompareStream`, parent `CompareView` (so Alt+↓/↑, F7, Ctrl+Alt+←/→, Ctrl+B, Ctrl+I and Alt+V are bound once), and a focus-path root. In `CompareStream`: J/K next/previous change (also Alt+↓/↑); Shift+J/Shift+K next/previous file (also Ctrl+Alt+↓/↑); V Viewed; O fold; Enter open the file diff; `/` search; Ctrl+Shift+←/→ copy all matches; Ctrl+Z `files.undo`. In `CompareView`: Ctrl+Alt+↓/↑ next/previous file; Ctrl+Z `files.undo`. In `Compare`: Alt+F `compare.stream` (free there; Alt+F is `viewer.follow` only in the viewer). A card with no open hunk (folded, viewed, summary) is one stop for J/K. Letters type into the search field while it has focus. All keys rebindable (D49).
- **D28 — Viewed.** Key: BLAKE3 of the left raw bytes followed by BLAKE3 of the right raw bytes (32 zero bytes for a missing side), 64 bytes. The app hashes while it reads a pair for its card. Stored in a new `compare-viewed` CacheDb table (key → time set), budget 4 MiB, oldest out. A pair whose content changes gets a new key and shows unviewed again. The key holds no path: identical content elsewhere also shows Viewed. "Viewed n of N": N counts Stream items without the same-after-rules group.
- **D29 — Copy one change (release 2).** Immediate, no sheet. The UI sends the pair, the hunk's byte ranges and its 128-bit digest. The app opens fresh apply sources (`PagedFile` for local files, the blob bytes for a Git side, which `[u8]` already serves as `ByteSource`), diffs the pair again on separate instances (engine rule 6), and copies only when a hunk with the same ranges and digest exists; otherwise "Changed since shown" and the card reloads. `apply_hunk` writes a staged file beside the target (engine rule 9). Then one `write_plan` job runs through the compare job factory (`JobSession::compare_factory`, session hold J4, retention J3b). Coarse, paged and token-cap hunks have no digest and are never offered. A Git or read-only side refuses with its reason.
- **D30 — Search (release 2).** Case-insensitive substring over the text of changed lines on both sides and over paths. Debounced 150 ms, tagged by a generation. The app searches the cards it holds first, then builds the missing ones with "Searching… n of N files". Esc stops and clears. Matching cards stay; inside them non-matching hunks fold into one row "N other changes".
- **D31 — Copy all matches as one job (release 2).** The plan sheet lists, per file, the matching hunks, bytes, and refusals (read-only side, not copyable, changed since shown). Enter runs: each file is re-diffed and digest-checked as in D29 and staged; every target stamp is checked before the first write; then one `Save` plan with one `WriteFile` per file (`write_many_plan`), one journal, one Ctrl+Z. A target that changes mid-run stops the job; files already written stay written, and Ctrl+Z undoes them. Part Y2 reuses the sheet. Base-aware (three-way) suggestions stay in Part M.

### Risks and rollback

- **R-V1, writing over a file that changed since it was shown.** D29's re-diff and digest match, `apply_hunk`'s revalidation (D101) and `WriteFile`'s stamp check refuse it. Tests in V26 and V31.
- **R-V2, a bulk job that stops halfway.** Stamps are checked before the first write; a later change stops the job, and undo reverts what was written. Tests in V25 and V31.
- **R-V3, memory on a Stream of thousands of files.** D26's card budget and the 2,000-row cap; V10 counts held bytes in a test.
- **R-V4, a stuck UI.** Every read, diff, hash and search runs on app threads (D24); the UI builds rows for the viewport only.
- **R-V5, undo under overwrite retention.** J3b puts the old version back *beside* the file as "… (restored)", not in place. Ctrl+Z after a compare copy therefore leaves two files when retention is on. Q5 asks the owner.
- **Rollback.** Every new command stays in `NOT_BUILT` (`commands/compare.rs:93-101`) until the atom that makes it work end to end; reverting one squash commit removes a slice.

Base: navo `main` 467718f4 (read only). Author: Turgon (architect). For the orchestrator to paste into

### Facts checked at 467718f4 (corrections to the brief marked ✱)

- `uniform_list` is built in `primitives/virtual_list.rs:208-218`; the file diff passes `.row_height` at `window_view/compare_screen/file.rs:237` ✱(not :253, which is `wrap_row`); large text at `large/list.rs:57-58`.
- `compare_diff::body::row_view` (`body.rs:220`) is used by `file.rs:231` and `large/list.rs:81` only. ✱Hex does not use it (`hex/draw.rs` uses the viewer's `hex_row_tinted`).
- `line_text` (`body.rs:97-116`) is `whitespace_nowrap().overflow_hidden()` and gives the whole line to `StyledText`.
- `wrap_row`, `Shape.starts` and `scroll_to_center` live in `file.rs:30-63,147-152,245-262`. ✱The copy bar (`copy/view.rs:41-65`) uses `at` only as the element id `("compare-file-row", at)`; hover goes by hunk.
- Today Shift+wheel scrolls the file diff vertically. gpui-windows turns Shift+wheel into `delta.x` (`vendor/gpui-pre-windows/src/events.rs:573-604`); X11 does the same. gpui's scroll listener then maps `delta.x` to y when `overflow.x` is not Scroll, unless `restrict_scroll_to_axis` is set (gpui-pre 0.3.12 `elements/div.rs:3406-3431`). `UniformList: Styled` exposes it as `style().restrict_scroll_to_axis`.
- F3 (`viewer/paged`) never wraps. It shifts text by 8 columns (`SHIFT_COLUMNS`, `paged/mod.rs:43,242-253`) on `viewer.scroll_left/right` (Left/Right). It cuts each line by character position (`paged/spans.rs:59-93 shown_text`). We reuse that idea, the commands and the 8-column step. The code stays separate, because F3 cuts raw file offsets (`u64`, `Painted`).
- The canvas probe pattern exists in `viewer/search/overview.rs:144-153` (`canvas` + `on_next_frame` notify). `Scrollbar::horizontal(..).viewport_from_layout()` exists in gpui-base 0.9.1 (`scrollbar.rs:856,911`).
- `unicode-width` 0.2.2 is already in `Cargo.lock` (transitive), and no navo crate uses it directly.

### Decisions

- **D39.1 Columns, not pixels.** Every cut works in display columns of the monospace font: tabs run to the next multiple of 4, wide characters take 2 (`unicode-width`), and control characters take 1 drawn as a space. A pure module `compare_diff::cols` measures and cuts lines. *Why:* we shape only the visible slice (today a 900 KiB line is shaped whole), the sizes are exact without laying out off-screen rows, and F3 already works this way. *Lost:* proportional fallback glyphs (emoji) may sit up to a column off.
- **D39.2 Shared offset.** `Sideways { offset, advance, text_width, widest }` sits in `Rc<RefCell<_>>` on the open `FileView` (and on `LargeShown`, D39.7). Both sides read the same offset. A new pair starts at 0. A layout switch keeps the offset, clamped. Its owner is the view; the bar handle and the wheel listener hold clones. Each row's text cell shows the columns `from = ⌊offset/advance⌋ .. from + ⌈text_width/advance⌉ + 2` and moves left by `offset − from·advance` px (`ml(-nudge)` inside the cell's `overflow_hidden`). Line numbers, ticks, the W6 edge bar, the copy bar and the change map sit outside that inner text div, so they never move.
- **D39.3 Input.** (a) One wheel listener on the list reads only `delta.x`: `Lines(d)` → `d.x × advance`, `Pixels(d)` → `d.x`, then `offset = clamp(offset − dx, 0, max)`. (b) `VirtualList::axis_locked()` sets `restrict_scroll_to_axis` on the file and large lists, so horizontal deltas no longer scroll vertically and a touchpad gesture keeps one axis. (c) A strip under the list carries one `Scrollbar::horizontal(handle).viewport_from_layout()` per text column (one in unified). Its height is `Scrollbar::width()`, and its overlay sits at the probed text cell's x and width. It is hidden when `max == 0` or wrap is on. (d) Keyboard path (design rule): Left/Right in `CompareView` run the existing `viewer.scroll_left/right`, 8 columns, as in F3.
- **D39.4 Extent.** `max = max(0, (widest + 1) × advance − text_width)`. `widest` is the largest `line_cols` of the pair, measured once per `PairText` on `cx.background_spawn`. The measurement keeps a dense `Vec<u32>` per side (4 B per line) and takes a fast path for printable-ASCII lines (`cols = len`). Until it lands, `max = 0`. A result for a `PairText` that is no longer open (`Arc::ptr_eq` fails) is dropped. `advance = ch_width(resolve_font(mono_font), typography.small)`, read in the rows closure each frame; when it is ≤ 0 (test text system), use `0.6 × small`. `text_width` comes from a `canvas` probe in the first built row's text cell(s). When it changes, call `window.request_animation_frame()`.
- **D39.5 Wrap = more list items, same row height.** `uniform_list` stays. With wrap on, a list item is one *visual line*. Pair row r takes `h(r) = max over its shown sides of max(1, ⌈cols/W⌉)` items, where `W = ⌊text_width/advance⌋ − 1` (at least 8; one column is slack for a wide character that starts last). A visual line k shows the characters whose start column is in `[kW, (k+1)W)`; a zero-width character stays with the one before it. Lines over `LONG_LINE` (1 MiB) count 1 and keep "Show bytes here". The shorter side's later items draw empty, with the row's wash or hatch, so the pair stays aligned. Later items have no number, tick or button. The current-hunk mark and the copy bar's hover cover every item; the bar sits on item 0 of the hunk's first row.
- **D39.6 Wrap index.** `WrapIndex` holds only tall rows: sorted `(row, extra)` plus a prefix sum of the extras before each, so `first_of(row)` and `at(item) → (row, sub)` are binary searches. It is built per `(layout, W)` in one pass over `pair_rows` in chunks of 65,536 rows: O(rows) with O(1) lookups, under 1 ms for 200,000 rows and 16 B per tall row. Nothing is measured up front beyond D39.4. `W` changes only when whole columns change, not on every resize pixel. When the key changes, the view keeps the top pair row: it reads `at(top item).row` before the rebuild and calls `scroll_to_top(first_of(row))` after. Order in `list()`: index → centre → seek. `Shape.starts` stay in pair rows. `go_to`, centre, map jump, seek and reveal convert with `first_of`. `built` records *pair* rows, so the change map viewport and the span requests (`file/spans.rs`) do not change. The map stays proportional to pair rows. Flat (no index) when wrap is off or the widths have not landed.
- **D39.7 Bodies.** Hex never wraps and never scrolls sideways. The large (paged) text body scrolls sideways, but `widest` is the largest line *seen* so far (`LargeShown::add_lines`, never lowered), so the bar's extent grows as you scroll. It never wraps: its `RowMap`/`FileBar` math assumes one row per line. The View menu shows "Wrap lines" only for an opened text pair.
- **D39.8 Toggle.** `compare.toggle_wrap` (`compare::ToggleWrap`, context `CompareView`, Alt+Z) flips `Look.wrap`, which defaults to off. `Look::choose` keeps it, so Simple/Rich/Custom do not touch wrap. It lives in `Look`, so it lasts for the compare-screen session: it carries between the Stream and the file diff (`mod.rs:285-292`), like the layout and the other View-menu choices. It resets when the screen closes (Q3). With wrap on, sideways input is ignored and the offset is kept for when wrap goes off.
