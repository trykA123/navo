# Speed phase · Navo feels instant on a locked-down Windows laptop

Status: planned (starts after OF1–OF8) · Started: 2026-10-28 · Replaces the parked P28 (`plans/2026-10-19-p28-real-pc-startup.md`)

## Goal

Navo feels faster than Total Commander on the owner's Windows work laptop (i7 12th gen, Intel UHD, CrowdStrike and corporate antivirus). On Linux it already feels snappy; on that laptop every file open, write, flush, rename, DLL load and process start costs extra, so the plan removes work from the UI thread and removes work that is not needed at all.

Inputs: `docs/perf.md` (owner-PC numbers), `docs/research/2026-10-28-perf-audit-sol.md`, `docs/research/2026-10-28-perf-audit-gemini.md` (checked; its exe-strip claim is wrong for MSVC), `docs/research/2026-10-28-*.md` (libraries), the UX stress test report (pending).

## Targets (owner's work laptop)

| Measure | Today | Target |
| --- | --- | --- |
| Summon from tray | — | ≤ 50 ms |
| Warm start to first usable | 540–590 ms | ≤ 250 ms |
| Cold start to first usable | 1.7 s | ≤ 800 ms (the rest is antivirus before `main`) |
| Key press to frame, 50k-file folder, 4 panes | not measured | p95 ≤ 16 ms |
| Open a 100k-file folder | not measured | ≤ 200 ms to first rows |
| Idle wakeups | 3 polling loops | none outside VSync of a focused window |
| Private bytes, two panes, idle | ≈ 137 MB | < 80 MB (driver share measured first) |

## Decisions

- SD1 · Measure first. No atom merges without a before/after number on the owner's laptop or the slow-disk shim.
- SD2 · The UI thread never waits on disk, registry, COM, SQLite, clipboard or process start.
- SD3 · Durable data keeps its guarantees: the operations journal and the safety net stay `synchronous = FULL`. Expendable state (history, cache ages, settings echo, logs) is batched.
- SD4 · No speculative work that loads foreign code: the Windows shell menu is built only on right-click or Shift+F10.
- SD5 · New dependencies only from the research shortlist, pinned, permissive licences, behind a measurement.
- Owner questions (open): see the end.

## Risks and rollback

- Resident instance keeps memory while hidden: opt-in setting; Quit is explicit.
- Off-UI sort and filter can show stale rows: every result carries the listing revision; stale results are dropped.
- Batched writes can lose the last seconds of history or cache ages on a crash: accepted for expendable state only (SD3).
- Each atom is one squash commit; rollback is a revert.

### SP0 — Measure
- **Change:** `tracy` cargo feature with `tracy-client` =0.19.0 + `tracing-tracy` =0.12.0 (as Zed's `ztracing`; named `tracy` so it does not clash with `--trace`, speed-atoms D5). `--trace <file>` writes one JSON line per input: action, key-to-present ms, UI-thread busy ms, disk calls. - **Check:** a test that the shim delays a listing; `--trace` output parsed by a test; the owner runs the trace build for one work day.

### SP1 — No idle wakeups
- **Change:** instance pipe waits on an event (our own overlapped I/O; `interprocess` is not needed, D88) instead of 200 ms polls; index activity arrives on a channel instead of a 500 ms poll (off when the index is off); drives refresh on `WM_DEVICECHANGE` plus on demand instead of every 2 s; VSync device checks stop while the window is inactive (vendored gpui).

### SP3 — Prefetch with a budget (done 2026-10-28; UNC paths count as network)

## SP13 · navo-bench

Status: v1 planned (decisions D90–D98 decided, D99 proposed) · Idea: Eru (owner), 2026-11-02 · Architect: Elendil (Turgon) · Branch: one `nb<id>` branch per atom from `main`

### Goal

Eru double-clicks `navo-bench.exe` next to a tester `navo.exe` and optionally picks one of his folders. He gets one HTML report and one JSON file next to the exe: start-up, idle, index, an anonymous profile of his folder, and how fast Navo lists, sorts and filters it. Each number sits next to its v1.0 target with pass or fail. He does not decide what to measure. The tool cannot change any file of his and cannot leak a name or path.

v1 is deliberately small (owner, 2026-11-02: "not extremely complex"). It has about 15 build atoms. Everything else is in "Later, if useful" below, parked, not deleted.

- **Non-goals in v1:** in-app script mode, write tests (copy, rename, multi-rename, delete), library baselines, the old-vs-new and Defender on/off double runs, tray summon, release builds, admin rights, Linux.
- **Alternatives considered:**
  - A PowerShell script plus xtask (first shape). Lost: corporate policy may block scripts, and xtask is not shipped.
  - Measuring inside `navo.exe` only. Lost: start-up, memory and wakeups must be seen from outside, and release `navo.exe` stays free of bench code.
  - An in-app `--bench-script` in v1. Lost to complexity: about 12 atoms. Outside timing covers the main targets (D99).

### Spec (what the owner gets)

1. **Start.** Double-click, or run `navo-bench.exe [--folder <path>] [--quick]`.
   - It finds `navo.exe` next to itself. It stops with a plain message if that is not a tester build (a `--metrics` probe exits with 2) or if another navo-bench runs.
   - It warns, without killing anything, when another Navo runs, the laptop is on battery, or the CPU was busier than 20 % in the 5 s before a round.
2. **Run root.** `%LOCALAPPDATA%\navo-bench\run-<time>-<4 hex>`, or `<drive>:\navo-bench-<time>-<4 hex>` on the owner's folder's drive when that needs no admin.
   - In v1 it holds only what the tool makes: CI fixture `A` (5,000 files) and `B` (200 × 25), the generated 100k folder (D98), the fresh exe copies for cold starts, Navo's profiles and `--metrics`/`--trace` files, and the run log.
   - Nothing of the owner's is ever copied in v1.
3. **Navo itself** (on fixture A and B, so numbers line up with `docs/perf.md`):
   - Cold start: 3 launches, each from a fresh copy of `navo.exe` and `pdfium.dll`. Antivirus scans each new file; this is not a reboot-cold start, and the report says so.
   - Warm start: 1 discarded warm-up, then 20 launches with `--metrics <file> --profile <root>\profiles\<n> --left A --right B`. Each gives first frame and first usable; the tool adds the time to a visible main window.
   - Idle: one plain launch. After 30 s: private bytes and working set. Then 60 s focused: CPU time and wakeups per second, with the VSync thread shown apart. Then 30 s minimised.
   - Exe size.
4. **Index:** `navo.exe --bench index --json` (exists in tester builds). It gives service state, first answer, latency per query id (q1–q5, never the text) and service memory.
5. **Machine:** core count, RAM, disk type, free space, Windows build, Defender real-time state. No user name, no machine name.
6. **The owner's folder** (skipped when no folder is given or the picker is cancelled):
   - A native folder picker opens. Refused folders are listed under (f).
   - Manifest before.
   - Data profile: one read-only walk.
   - Folder timings (D99), 5 runs each:
     - **Headless pipeline:** `navo.exe bench --folder <path> --filter <prefix> --out <root>\…json` (new, NB12). Numbers: entries, list ms, each sort ms, each filter keystroke ms.
     - **Window start:** `--metrics --left <folder> --right A`. Number: first usable with the folder in a pane.
     - **Window keys:** `--trace` with `--left <folder>`. The tool posts Down ×100, PageDown ×20, the filter prefix and Esc to Navo's own window. Number: key-to-frame p95 from the trace.
   - The same three on the generated 100k folder, unless `--quick`.
   - Manifest after. Any difference prints "DATA SAFETY: your folder changed" with counts only, sets exit code 3 and keeps the redacted run log.
7. **Cleanup.** The run root goes to the Recycle Bin in one move, and only when its marker matches. A crash or Ctrl+C leaves the marker, and the next start finishes the cleanup.
8. **Output.** `navo-bench-<yyyymmdd-hhmm>.html` and `.json` next to the exe. The console says only that the two files were written.

**Not measured in v1, listed under "later":**
- Sort and filter time-to-rows inside the window. Above 20,000 rows they are async; only the headless pipeline times exist.
- Sort key-to-frame. `Ctrl+F3`–`F6` needs real modifier state, which a posted message does not carry.
- Ctrl+K typing-to-results in the window. The service query latency from `--bench index` stands in, labelled "service, without UI".
- Preview and PDF first page; write timings; tray summon.

#### How the numbers are computed (D93)

- Median: the middle sample; for an even count, the mean of the two middle ones (as `xtask/src/stats.rs`).
- p95: nearest rank, `sorted[ceil(0.95 × n) − 1]`. With fewer than 20 samples the report labels it "max".
- Wakeups per second: the context-switch deltas of all Navo threads (`NtQuerySystemInformation(SystemProcessInformation)`, no admin; `SYSTEM_THREAD_INFORMATION.Reserved3` in windows-sys 0.61.2), summed and divided by the window's seconds.
- Memory: `GetProcessMemoryInfo` `PrivateUsage` and `WorkingSetSize`, the same source as `--metrics`.
- Open 100k: the headless list ms on the generated folder. It has no frame, and the report says so. "First usable with the folder" is shown beside it.
- Noise: a warm-up round is discarded. A measure is "noisy" when its interquartile range exceeds 15 % of its median. Each verdict names its sample count.

#### Data safety (hard rules; each with its own test; built first)

- **(a) Read-only.** The owner's folder is read only through `ReadOnlySource`: folders with `FILE_LIST_DIRECTORY`, files with `GENERIC_READ`, sharing read, write and delete.
  - It has no write method.
  - The crate's `clippy.toml` disallows every `std::fs` write, rename, remove, link and permission call, plus `OpenOptions::write/append/create/truncate`. Only the guard module may use them, under `#[expect]`.
- **(b) Writes stay in the run root,** which is never inside the owner's folder and never contains it.
- **(c) One guard module:** `navo-bench/src/guard/`. Every write, copy target, rename and delete goes through `ScratchRoot::check`.
  - It refuses relative paths, `..`, device and `\\?\GLOBALROOT` forms, and alternate data streams.
  - It resolves the deepest existing ancestor with `GetFinalPathNameByHandleW` (follows junctions, symlinks, 8.3 names, `subst`) and compares components case-insensitively with the root's final path.
  - It refuses any reparse point inside the root.
  - The module is complete in v1 although v1 only creates files, copies the exe and recycles the root. It is the gate for every later write test.
- **(d) Recycle Bin only,** after the guard, and only on a fixed local drive. A delete that would become permanent is refused. In v1 the only delete is the cleanup of the run root.
- **(e) Cleanup** recycles only the run root, and only when `.navo-bench-root` holds the token recorded in `%LOCALAPPDATA%\navo-bench\pending.json`.
- **(f) Refused test folders:**
  - drive roots and `%WINDIR%`;
  - both Program Files folders and `%PROGRAMDATA%`;
  - `C:\Users` and every user-profile root;
  - the exe's folder and the run root;
  - any folder that contains or lies inside one of these.
  - Lookups use known folders (`SHGetKnownFolderPath`), not string guesses.
- **Proof (manifest).** It records, for every entry of the owner's folder, the relative path (in memory only), kind, size, last-write time and attributes, and each folder's entry count and last-write time. It also holds BLAKE3 hashes of a fixed set of up to 1,000 files and 1 GB. Before and after must be equal.
- **Navo on the owner's folder** only lists, sorts and filters. The tool posts only Down, PageDown, letters and Esc, and only to Navo's own window (never `SendInput`). NB14 confirms in the default keymap that none of these keys starts a write in the file list. Navo runs in a Job object with kill-on-close.

#### Privacy (hard rule; its own test)

- The report, the JSON, the run log, the console and panic messages hold:
  - no name or path from the owner's folder;
  - no user or machine name;
  - no file content;
  - no query or filter text.
- Allowed: counts, sizes, depths, timings, buckets and folded extensions (D92: an extension shows only when seen on ≥ 10 files in ≥ 2 folders and made of ≤ 8 ASCII letters or digits).
- Report types carry numbers, enums and fixed labels only. Errors carry a kind and a path role, never a path. The panic hook prints the source location only.
- `SafeWriter` is the only sink. It scans with `aho-corasick` for the folder path and its components, user and machine name, the profile path, and walked names of ≥ 6 characters (up to 200,000). Each is scanned as UTF-8, UTF-16LE, percent-encoded and JSON-escaped. On a hit, it writes a stub with the count only.
- The filter prefix is 3–5 letters of a real name, held in memory. It reaches Navo only as an argument and as posted characters.
- Navo's trace, metrics and crash records stay in the run root and go to the Recycle Bin with it.

### Risks and rollback

- R1 — The tool or Navo writes into the owner's folder. Prevented by (a)–(f), the read-only key set and the manifest proof. The VM proof adds an independent PowerShell hash list. Every data-safety atom is senior, with a Sonnet-high review plus Sol xhigh when Codex has usage.
- R2 — A name or path leaks. Prevented by typed reports, `SafeWriter` and the planted-name test.
- R3 — The Recycle Bin deletes permanently without asking. NB3 must show that `trash` 5.2.9 (the shell no-UI, allow-undo and nuke-warning flags) cannot do that silently. Otherwise NB3 uses `IFileOperation` with `FOFX_RECYCLEONDELETE`, which fails instead (orchestrator's stop rule).
- R4 — Posted keys behave differently from real keys. NB14 checks that the trace records them. If not, key-to-frame moves to "later".
- R5 — 100k empty files take minutes under corporate antivirus. Accepted: the time is shown, and `--quick` skips them.
- Rollback: one squash commit per atom; `git revert <sha>`. The tool is not in release builds.

### Briefs for the data-safety atoms

- **NB2–NB3.** Read: `navo-fs/src/local/ops.rs:240-275` (`recycle` through `trash`). `trash` source: `windows.rs:97`.
  - Every write method takes `&Guarded`, never a `Path`. `Refusal` is an enum without a path.
  - Stop if `GetFinalPathNameByHandleW` cannot resolve a junction without admin.
  - Stop if `trash` can delete permanently without asking (R3). Then the fail-closed `IFileOperation` path comes first.
- **NB4.** The walk never enters reparse points; it counts them.
  - Content reads (manifest hashes, the NB13 sniff) use `GENERIC_READ` and share all.
  - The share-mode test runs while a walk and a read are in flight.
- **NB6.** `SafeWriter::write(role, bytes)` is the only file and console sink. Panic payloads are never printed.
- **NB14.** Read: `crates/navo-app/src/bench/listing.rs`, `crates/navo-ui/src/window_view/input_trace.rs:1-120`, the default keymap.
  - Posted keys: `WM_KEYDOWN`/`WM_KEYUP` for Down, PageDown and Esc; `WM_CHAR` for letters.
